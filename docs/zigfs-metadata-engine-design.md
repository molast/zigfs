- 位置：[`pkg/metadata-engine`](../pkg/metadata-engine/README.md)
- 工具链：Zig 0.17.0；package 版本 0.3.0；WAL / Snapshot 统一 v3，不兼容旧格式
- 状态：已于 2026-11-18 接入 ZigFS，旧元数据存储已移除；目标平台验证仍待完成

## 1. 目标与接入边界

独立包保存 `(record_type, key) -> generation, tombstone, payload`，payload 不透明。
遵循当前 MetadataRepository 的条件写入、类型隔离、结果所有权和排序语义，增加
批量事务、有界查询、FIFO 提交、Group Commit、分段 WAL 与后台快照。

ZigFS 已通过 `metadata/engine_repository.zig` 接入独立引擎，数据直接保存到
`ZIGFS_DATA_ROOT/.zigfs.sys/`（默认 `data/.zigfs.sys/`）。旧 `.record` 和独立 journal
存储、旧恢复器与 generation 文件已删除。业务 payload、查询索引和对象内容职责保留。

| 现有项目模块 | 关系 |
| --- | --- |
| `ports/metadata_repository.zig` | 包内接口形状和基础语义来源；类型身份不同，未来需适配器 |
| `metadata/local_repository.zig`、`local_journal.zig` | 将来的替换候选，本阶段不调用或修改 |
| `metadata/index.zig` | 现有业务列表索引；不会因独立包有 AVL 就自动替换 |
| `metadata/*_store.zig`、`*_payload.zig` | 保留业务模型与编码，包不复制这些模型 |
| `application/mod.zig` | 未来负责后端选择、恢复状态映射和生命周期装配 |
| `backend/local.zig` | 原实例锁与数据根格式防护仍需保留 |
| `application/object_gc.zig` | 继续负责对象引用及数据 generation 回收 |

必须覆盖 system、bucket、object、multipart、credential、directory 六个记录域。
当前对象历史版本聚合在单个记录中；身份、角色、策略、标签和系统配置已进入引擎的 13 个业务命名空间。
实时监控仅使用内存，历史监控采用每 60 秒批量保存的独立文件；详见接入记录。
替换 repository 不会自动统一这些数据，也不会自动消除长版本历史的重写成本。

## 3. API、语义与所有权

| API | 行为 |
| --- | --- |
| `Engine.open / openWithOptions` | 独占打开专用目录，校验并恢复 |
| `engine.interface()` | 兼容语义的 get / put / tombstone / scan |
| `engine.commit(mutations)` | 一个原子事务，多条记录共享新 generation |
| `engine.commitGroup(items)` | 按顺序执行独立事务，合并最终 WAL sync，分别返回结果 |
| `engine.scanPage(...)` | AVL seek、有界访问和字节预算 |
| `engine.checkpoint()` | 捕获一致视图，锁外写快照，安全安装和回收 |
| `engine.collectTombstones()` | 显式回收删除标记、持久化缺失世代并收缩索引；阻塞式维护 |
| `engine.backup(parent, name)` | 在线固定视图导出，发布独立可恢复目录，不覆盖已有目标 |
| `engine.stats()` | 健康状态、数据量、WAL、同步、恢复和维护指标 |
| `runtime.start / stop / interface / commit / stats` | 可选提交协调与后台维护 |

`.any` 无条件更新；`.missing` 要求记录不存在且 gc_epoch 为零，tombstone 仍算存在；
`.{ .missing_at = epoch }` 要求记录不存在且 epoch 与当前回收世代相同。启用物理回收前
必须将所有创建调用者改用 missing_at；取世代应先于“不存在”的业务判断，Conflict 后
重新判断业务，不能仅刷新世代盲目重试。`.exact` 要求当前记录 generation 匹配。
条件失败返回 Conflict，不产生该事务的部分修改。
批次内重复 `(type,key)` 被拒绝；跨事务的同 key 修改按提交顺序检查条件。

generation 为事务序号，不是 S3 Version ID 或对象数据 UUID。成功事务严格递增；
溢出拒绝继续提交。快照保留每个记录原 generation，恢复继续递增。

Engine allocator 管理常驻记录、索引、编码缓冲及快照副本；get/scan/page 使用调用者
allocator 复制返回结果，并由调用者 deinit。HashMap 拥有共享记录节点及 key/payload，
AVL 借用同一节点。新键的节点在 WAL append 前预分配；覆盖更新保留键和节点，
仅替换 payload 和元信息。快照捕获直接遍历节点，避免逐键再次查询 HashMap。

Engine/Runtime 启用后不得移动。root 由调用者持有，生命周期长于 Engine。已入队 mutation
的 key/payload 在调用返回前保持有效且不变，因此入队后等待不可取消。stop 拒绝新提交、
排空已接收请求、等待维护退出；外部调用全部结束后再销毁 Engine。
后台快照与提交可同时分配内存，需线程安全 allocator。

## 4. 索引与有界查询

每个 namespace 有一个 HashMap 和一个 AVL 索引，均从持久化状态重建。
完整 key/payload 仍常驻内存；不是按需读取磁盘页的数据库。

- 精确 get 平均 O(1)，返回值复制成本与记录大小有关。
- AVL 插入、替换、seek 为 O(log N)，无随机优先级或退化成链的树形。
- scanPage 使用栈式 AVL 游标，一次 seek 后顺序遍历，索引访问为 O(log N + visited)。
  游标只在状态锁内有效，不增加每个节点的父指针或分页堆分配。
- 兼容接口 scan 按 AVL 顺序复制，省去额外排序，但仍为全量复制，不应当作有界分页使用。

分页参数：prefix、排他 start_after、limit、max_bytes、include_tombstones、可选
expected_generation / expected_gc_epoch。回收不增加事务 generation，所以一致分页必须
同时携带上一页的两个字段；世代省略时视为零。排序比较原始 key 字节，不做大小写折叠、路径规范化或 locale 排序。

limit 限制访问 key 数量，而不是仅限制返回记录，避免大量 tombstone 造成无界扫描。
过滤后可能有空页和有效 continuation；next_start_after 为空才表示结束。
结果 key/payload 总字节不能超过 max_bytes；第一条记录超预算时报 ResourceLimit，
否则在该条之前停止。后续调用须沿上次实际访问的 key 前进。

每页在状态锁内读取一致视图。expected_generation 不匹配时报 Conflict，调用者可从头
重试；未提供时是普通 keyset pagination，可能观察并发更新，不承诺跨页稳定快照。
S3 delimiter、CommonPrefixes、Version 列表排序和编码后的 continuation token 属于未来
业务查询适配层，不由引擎解释 payload 推测实现。

## 5. 提交调度与持久化

### 5.1 同步 Engine

所有读、写和索引发布受状态互斥锁保护。提交先校验条件、额度和编码限制，复制记录、
预留 HashMap 容量和 AVL 节点，再编码并追加一个完整事务帧。
单独 commit 调用 WAL sync 后发布索引并返回成功。

### 5.2 FIFO Runtime 与 Group Commit

Runtime 是可选层。请求按成功入队顺序处理，使用调用线程栈上的 request 和事件等待，
避免额外请求内存复制。队列满返回 Busy，不无界堆积。

协调器按数量、编码字节目标和固定等待截止时间取一组请求。每个事务独立校验、分配
和追加帧；同组后续条件观察之前事务的结果。组内索引可以先更新，但整个组始终持有
状态锁，读者无法看到尚未完成同步的状态。最后执行一次 WAL sync，成功后才逐个唤醒
调用者；每个事务仍有独立 generation 和独立恢复边界。

若某请求 Conflict、OutOfMemory 或 ResourceLimit，可单独失败，其余有效事务继续。
若追加/同步结果不确定，所有已进入待确认状态的请求返回 Unavailable，Engine 冻结，
禁止继续读写。未获得成功响应的完整事务可能在恢复后存在；不得声称失败等于回滚。

默认 max_pending=1024，最多 64 事务/组，目标 4 MiB。第二轮起，已有 8 个请求或达到
目标字节数便开始收集；孤立请求最多增加 25 μs 合并等待，其余情况最多 100 μs。
这些是计划等待上限，不包含 OS 调度、锁竞争与同步耗时。
合法但超过组字节目标的单事务独立成组。OS 调度可能延长实际等待。
FIFO 保证已接受请求的提交顺序，不提供操作系统线程调度或读锁获取的实时保证。

### 5.3 错误分类

保留原接口的 NotFound、Conflict、InvalidKey、PayloadTooLarge、OutOfMemory、
CorruptRecord、CorruptJournal、GenerationExhausted、Unavailable，增加：

- ResourceLimit：配置额度不足；与数据损坏不同，通常可通过 checkpoint 或配置调整解决。
- Busy：提交队列已满；open 的独占锁冲突也使用 Busy。
- ReadOnly：只读检查实例禁止写入。

文件打开、版本和恢复错误可由 open 返回更具体错误。未来接入需显式映射到应用状态和
HTTP 错误；不可直接假定新增包错误与现有 ZigFS 错误集合相同。

## 6. 磁盘布局与格式

```text
<专用目录>/
├── LOCK
├── wal                              # 当前活跃段
├── wal-00000000000000000000.segment  # base generation 命名的归档段
├── wal-00000000000000000042.segment
└── snapshot                         # 单个完整快照
```

首次初始化要求专用空目录。LOCK 已存在而 WAL 缺失时拒绝自动重建空库，包括初始化
中断的残留状态。禁止删除 LOCK 绕过独占锁。16 个小写十六进制字符的文件名保留给 Zig
0.17 File.Atomic 临时文件，只在成功恢复且未启动后台任务时清理；不递归、不删除其他名称。

### 6.1 文件头（80 字节）

| 偏移 | 长度 | 含义 |
| --- | --- | --- |
| 0 | 8 | `ZFMELOG1` 或 `ZFMESNP1`；Magic 保持稳定，版本由独立字段决定 |
| 8 | 2 | WAL / Snapshot 均为版本 3；其他版本明确拒绝 |
| 10 | 6 | Snapshot 为 u48 gc_epoch，小端并纳入校验和；WAL 必须零 |
| 16 | 8 | WAL base generation，或 Snapshot 一致视图 generation |
| 24 | 8 | Snapshot 条目数；WAL 为零 |
| 32 | 16 | 数据库随机身份标识 |
| 48 | 32 | 前 48 字节 SHA-256 |

显式 little-endian，不依赖 Zig 内存布局。Snapshot 与所有需要重放的段必须匹配数据库
身份。开发阶段不保留 v1/v2 兼容，不迁移；旧格式返回 UnsupportedFormat，启动时不
静默删除或重置。调用者停止旧实例后可删除旧专用数据目录，再初始化新库。
Snapshot 的世代随 checkpoint 和备份持久化；世代溢出拒绝回收，不能回绕。
不支持把 ZigFS 原 `.record` 目录当成此格式。v3 Snapshot 要求各命名空间内严格键序。

### 6.2 事务帧（继续使用帧版本 1）

64 字节帧头：Magic `ZFMETAW1`(8)、version(2)、flags(2)、整帧长度(4)、generation(8)、
mutation 数量(4)、reserved(4)、前 32 字节 SHA-256(32)。随后为 mutation 列表，末尾再附
32 字节 SHA-256，覆盖头部与列表。

mutation 头为 type(u8)、tombstone(u8)、reserved(u16)、key 长度(u32)、payload 长度(u32)，
随后跟 key/payload。tombstone payload 必须空。事务内禁止重复逻辑 key。

一个完整且校验通过的帧就是一个原子事务，不另写 BEGIN/COMMIT 文件。单帧最多 64 MiB
（包含编码开销），最多 4096 mutation，key 为 1–2048 字节且不含 NUL。
因此最大 payload 略小于原 `.record` 的 64 MiB payload 上限，未来适配须明确处理。

Snapshot 每条记录一个帧，保留原 generation，包括 tombstone。校验文件头、所有帧、
记录数量、重复 key、generation 边界与准确 EOF。SHA-256 只做损坏检测，不是加密或认证。

## 7. WAL 轮转与恢复链

段达到目标大小后，下次提交或 checkpoint 触发轮转。单事务和单个提交组不拆段，因此
目标段大小是软阈值；总 WAL 额度为硬限制，并为下一次轮转预留 80 字节头空间。

轮转顺序：

1. 同步当前 WAL。
2. 为当前 WAL inode 建立以 base 命名的硬链接归档（同一目录、同一文件系统），无需复制整段。
   仅在文件系统返回 OperationUnsupported 时，回退到完整复制、长度校验、文件同步和原子安装。
   权限、容量或 I/O 错误直接失败并冻结实例。
3. 同步归档所在目录，保证编号段名字先于新 WAL 持久化。
4. 创建新 WAL 头，base 为当前 generation，同步后原子替换活跃 WAL 并同步目录。
5. 切换句柄，之后的新提交从新段追加。

在第 3、4 步之间中断时，会有与活跃段相同 base 的冗余归档，恢复不能将它重放两次。
base >= 活跃段 base 的归档视为未安装轮转，成功恢复后可清理。
归档链接与旧活跃 WAL 暂时指向同一 inode；状态锁禁止轮转期间追加，任何轮转错误冻结实例。
新 WAL 替换并同步目录后才切换句柄。重开先验证恢复链，再删除未安装轮转的冗余名字，
之后才能接收新写入。缺段、错误数据库身份和 generation 连续性规则不变；当前文件头为 v3。
硬链接路径不复制数据；复制回退路径仍需要临时整段空间，磁盘规划须预留该空间。

恢复先读 Snapshot，再按 base 顺序验证所需归档段，最后读取活跃段。段内 generation
必须连续，归档末尾必须准确衔接下一段 base；缺段、重叠导致不连续、错误身份、完整帧
校验失败均拒绝启动。快照完全覆盖的旧段不再是事实来源，可以跳过并回收。

仅活跃段末尾的不完整帧允许截断。已封存归档段任何不完整内容都是损坏。完整帧即使位于
EOF，校验失败也不能自动截断。所有所需数据验证完成之后，正常 open 才修复活跃尾部、
同步并清理已覆盖段、未安装归档和已知临时文件。

## 8. 后台快照与安全回收

checkpoint 由独立快照锁串行化：

1. 获取状态锁，检查快照预算，一次分配固定视图数组。遍历记录，保存元信息与节点指针，
   借用稳定 key 并固定当前 payload，形成一致视图 S，不复制 key/payload 字节。
   节点的原子 pin 位使用既有填充空间，64 位目标上的节点大小仍为 64 B。
2. 将 WAL 在 S 处轮转，使后续写入位于快照边界之后；释放状态锁。
3. 在锁外逐帧编码，通过 64 KiB 缓冲写临时快照；先 flush 缓冲，再同步文件。
   帧布局和持久化边界不变，此时允许新写入和查询。
4. 重新获取状态锁，若引擎已进入错误状态则放弃安装。
5. 原子替换 Snapshot，目录同步成功后发布快照边界 S。
6. 在状态锁内固定回收边界和段清单，再释放状态锁进行已覆盖段删除和目录同步；
   每次成功删除短暂持锁更新 WAL 额度。快照锁始终串行化维护，写入只会创建捕获的
   active base 及其之后的段，不会重用选中的旧段名字。启动时还清理未安装轮转的冗余段。
7. 成功路径在状态锁外释放视图：原子交换 pin=false；若原值为 true，则当前节点仍拥有
   payload，不释放；若为 false，说明写者已将旧 payload 转交给视图，释放该旧值。
   第一次覆盖被固定节点也使用原子交换；得到 true 时保留旧值，得到 false 时正常释放。
   checkpoint_mutex 覆盖整个视图生命周期，避免前后两份视图交错及 ABA。
   若检查点先重试清理，重获锁后重新检查错误状态，
   防止清理期间失败的并发提交被冻结后仍继续写快照。

快照发布前失败，可依靠旧快照与保留的完整 WAL 链恢复。目录发布结果不确定时冻结引擎。
快照已持久化后，清理旧段失败不意味着新数据丢失，可在后续恢复或 checkpoint 重试。

首版只有一个快照，不支持损坏快照自动回退。未来若保存多个快照，必须同时保留从最旧
可回退快照到最新确认提交的 WAL 链，仅保留旧快照文件不能保证安全回退。

普通 checkpoint 保留 tombstone。显式 collectTombstones 在快照锁与状态锁下预分配
存活记录的新 HashMap，轮转 WAL，写不含 tombstone 且 gc_epoch 加一的快照，同步并原子
安装后才释放删除节点、键和值并重建 AVL。新世代与删除结果位于同一校验文件中，恢复
不会出现“记录已回收而世代未更新”。版本号不回绕，旧 exact 无法匹配重建后的记录。
回收可释放记录额度并收缩映射容量，但会阻塞读写；没有后台自动或增量物理 GC。
对象内容、历史版本和 multipart 业务回收不属于此包。

Runtime 默认每秒检查一次，只有存在新 generation 才考虑 checkpoint。第二轮默认自适应策略：

- 最小 WAL 门槛为 min(32 MiB 配置值，WAL 额度 / 2)；动态目标为
  min(WAL 额度 / 2，max(最小门槛，当前逻辑数据字节数))。
- 达到最小门槛后，WAL 达动态目标或累计修改字节达到当前逻辑数据的一半即可触发。
  `dirty_bytes` 是提交的 key/payload 累计体积，并非去重后的脏键数；快照只减去捕获时的计数。
- 普通维护与上次结束时间的间隔至少为上次维护耗时的 4 倍；WAL 压力或额度达到 75%
  绕过门槛和冷却。失败清理优先独立重试，不受自适应门槛限制。
- `adaptive_checkpoints=false` 可恢复固定 WAL 门槛策略；
  `checkpoint_cooldown_multiplier` 默认 4。减少快照会保留更多尾部 WAL，可能增加重开耗时。

维护失败记录计数及最近错误，不静默丢弃；错误状态引擎不再接受维护写入。

## 9. 资源限制与可观测性

| 额度 | 默认值 | 精确边界 |
| --- | --- | --- |
| max_records | 100 万 | 包含 tombstone |
| max_live_bytes | 512 MiB | 所有 key + payload 字节，不含索引、分配器等开销 |
| max_snapshot_bytes | 512 MiB | 捕获时视图覆盖的 key + payload 逻辑字节（不含视图数组） |
| segment_bytes | 16 MiB | 轮转软阈值，不拆事务/提交组 |
| max_wal_bytes | 1 GiB | 活跃段和保留归档的逻辑文件大小；不含临时副本、Snapshot |
| max_page_records | 1 万 | 单页访问数量 |
| max_page_bytes | 16 MiB | 单页返回 key + payload |
| max_pending | 1024 | Runtime 排队及处理中请求数量 |

额度在提交前验证，不以部分更新的方式失败。编码帧、预分配、快照条目和 HashMap/AVL
都会产生额外内存；这些是工作量限制，不是严格进程 RSS 限制。恢复同样检查记录和逻辑
内存额度；历史 WAL 超出新配置额度时允许完整恢复，随后写入受限，可 checkpoint 回收。

Engine 指标含 generation、checkpoint_generation、records、live_bytes、wal_bytes、
active_wal_bytes、commits、syncs、groups、rotations、checkpoints、recovered_frames、
incomplete_tail_bytes、orphan_temporaries_removed、recovery_required。
commits 统计本次进程确认持久化的事务；syncs 仅统计提交 WAL 同步，不含维护同步。
错误状态下内存 generation 与物理 WAL 结果可能不一致，不能用指标宣称事务已确认。

Runtime 指标含 queued、in_flight、peak_pending、groups、transactions、rejected、
checkpoint_failures、last_checkpoint_error。Runtime transactions 为处理的请求数，可能
包含冲突等失败；不等于 Engine 成功提交数。计数指标重启归零。

## 10. 离线运维工具

`metadata-tool inspect|recover|checkpoint DIRECTORY [max_records] [max_live_bytes]`。
工具获取独占锁，不能与运行中的引擎同时操作。JSON 输出到 stdout，失败返回非零。

- inspect：只读校验，不创建文件、不截断尾部、不清理任何文件；可报告未完成尾部。
- recover：验证后仅截断不完整活跃尾部，执行安全启动清理。
- checkpoint：正常恢复后安装新快照。

工具不会跳过损坏帧、重置损坏实例或强行恢复未来格式。检查也需要内存索引，资源限制
可通过参数调整，不能将 ResourceLimit 当作 CorruptRecord。

手工复制源库仍需停止 Runtime 和全部外部请求、关闭引擎，再复制整个专用目录，不能
遗漏增量 WAL。新增 backup(parent, name) API 可在线捕获固定视图并锁外写入独立目录，
包含该边界的 snapshot、同边界空 WAL 和 LOCK。全部文件及临时目录同步后，使用不覆盖
rename 发布正式名字并同步父目录。成功输出可直接打开；中断可能留下私有临时目录，
发布后同步错误则可能留下完整目标。源库不会因目标 I/O 失败被冻结。
备份、checkpoint 与 GC 共享快照锁；备份期间读写继续，但检查点推迟可能造成 WAL
额度背压，覆盖旧值可能增加临时内存。恢复后必须废弃旧实例条件令牌，不能跨恢复沿用。
此包的备份也不是完整 ZigFS 备份，详细接口与边界见
[维护功能说明](../pkg/metadata-engine/bench/MAINTENANCE-VALIDATION.md)。

### 14.1 共同基线与执行规则

- 固定同步等级、数据量、payload、并发、批量大小、缓存状态和构建模式，保存二进制
  标识与原始结果。普通同步、F_FULLFSYNC、MS_SYNC 不能混成同等断电保证的吞吐排名。
- 主要比较 1 万、10 万、100 万条的分阶段耗时、整轮耗时、常驻/峰值内存、吞吐、
  P99/P99.9、最大停顿和维护次数；注明测试轮数，不只报告平均值或最好的一轮。
- 每步独立修改、独立对照，不同时更换多种核心结构。测量指标自身的开销也需核对。
- 单项实测最多 10 分钟；预计超过时限的性能项目可以预测，但必须注明模型和依据。
  中止、预测和实测通过分开记录，不预测内存或把未完成校验标为通过。
- 正确性、断电恢复、长期泄漏/压实/GC 不能预测通过。当前时限下未覆盖的长期行为
  保留为“未验证”，不以反复重启的短测试代替同一进程长期运行。
- 每步运行与改动相关的单元、所有权/OOM、并发和恢复测试；修改持久化协议时补齐
  实际强杀边界。不得减少同步、放宽校验或跳过失败轮次来换取成绩。

### 14.2 第一轮：重开速度与内存

目标：减少恢复路径的小块 I/O 和分配，降低记录/索引维护开销；先拆清楚内存组成。

| 工作 | 实施方案 | 重点约束 |
| --- | --- | --- |
| 恢复顺序读缓冲 | 使用有界缓冲顺序读取，复用帧缓冲区，减少逐帧小块读取和临时分配 | 保留帧长度、checksum、generation 链和文件身份校验；只有活跃 WAL 不完整尾部可修复 |
| 索引容量预留 | 根据经过校验的快照记录数预留容量 | 不直接信任磁盘声明值，受资源额度和整数溢出检查约束 |
| 批量构建有序索引 | 研究按命名空间和键顺序写快照，恢复时批量构建索引，减少逐条插入和树旋转 | 明确排序保证、格式标识和恢复行为；不能假设现有快照天然有序 |
| 覆盖路径复用 | 保留已有键和索引节点，更新时主要替换值，减少反复分配、删除和重插 | 分配失败不得部分发布；提交、读可见性和同步失败语义保持一致 |
| 共享记录所有权 | 梳理 HashMap、AVL 与记录之间的键、元信息和引用，减少重复存储 | 明确借用、拥有和释放责任，避免悬挂引用、重复释放及扫描结果失效 |

首先在写入结束、更新结束、分页、全量扫描、快照、重开后分别采样进程内存，并统计
引擎持有的分配字节数。区分常驻记录/索引、扫描结果、快照副本与分配器保留内存。
此前约 800 MiB 是整个百万条测试进程的峰值，不能直接当成引擎稳态常驻内存。

已有实验中，大块连续快照副本增加了峰值 RSS，不直接重新采用。先减少重复分配和
复制，再评估专用内存池；内存方案必须同时检查峰值和释放后占用，避免只让复制更快。

**验收：** 同条件百万条重开耗时下降，分别记录常驻及峰值内存变化，明确收益来自哪个
阶段；校验、损坏检测、资源额度、OOM 和结果所有权测试不退化。不预先承诺未经实测的
加速倍数或内存目标，保留仍未改善的指标。

**第一轮实施结果（2026-11-17）：** 上表五项均已落地。使用 64 KiB 恢复读缓冲与可复用
大帧存储；校验快照后按命名空间预留 HashMap，借用帧解码器减少临时分配；新快照按键
写入并在读取时验证顺序，旧无序快照排序后批量建 AVL。HashMap 拥有共享记录节点，
AVL 借用节点，覆盖更新复用键和节点。文件格式仍为 v2，未接入 ZigFS。

1 万/10 万/100 万条各交替测试三次，快照重开分别约快 3.65/3.58/4.02 倍。
百万条快照重开中位数 2.758 s → 0.685 s；进程峰值 RSS 中位数 806.6 → 742.6 MiB。
独立内存采样中，引擎稳态请求分配 434.2 → 377.1 MiB；关闭后跟踪分配归零。
这是热缓存、本机短测，不代表冷缓存或 NAS 结果。

本轮也记录到代价：百万条更新 QPS 中位数下降 6.4%，更新 P99 增加 23.4%，
手动 checkpoint 增加 23.2%。因此第一轮结论限定为“重开明显改善、内存下降”，
不能称为所有维度提升；第二轮优先处理快照复制临界区和写入尾延迟。
第一轮当时未输出 P99.9；第二轮已补齐并用带相同采样逻辑的第一轮构建重跑基线，不以 P99 或最大值代替。
详细数据、45 项单元测试及恢复验证见
[第一轮优化报告](../pkg/metadata-engine/bench/ROUND1-OPTIMIZATION.md)。

### 14.3 第二轮：写入尾延迟

目标：定位慢请求的等待来源，优先减少可避免的轮转和快照停顿。

先增加阶段指标：

| 阶段 | 需要回答的问题 |
| --- | --- |
| 请求排队 | 慢请求主要在等待前面多少事务？队列长度和等待时间如何变化？ |
| Group Commit 收集 | 合并等待是否过长？实际组大小与吞吐/尾延迟有什么关系？ |
| 状态锁等待与持有 | 是快照、轮转、读取还是提交占用了状态锁？ |
| WAL 追加与同步 | 时间花在写入还是设备同步？同步等级是否一致？ |
| WAL 轮转 | 是否出现与段边界对应的周期性停顿？ |
| 快照捕获与安装 | 锁内视图复制、安装和清理分别阻塞了多久？ |

按测量结果实施：

1. **WAL 无整段复制轮转。** 借鉴 Pebble 的日志生命周期，研究不可变编号段与新段切换，
   减少持锁复制整个活跃日志。先明确段身份、连续 generation、封存/新建顺序、文件与
   目录同步、缺段及孤儿段处理，再实现并强杀验证各边界。这属于持久化协议变更。
2. **后台快照调度。** 综合新增日志量、脏数据量、额度压力和上次维护耗时安排快照，
   避免快照变快后更频繁打断前台。保留额度压力触发、失败重试和背压，不能因限速
   导致额度耗尽后永久停止写入。
3. **按负载调整合并等待。** 队列已有足够请求时尽快提交，低负载时限制额外等待。
   同时比较吞吐与尾延迟，不以提交组越大越好为目标。
4. **保留当前提交可见性边界。** 暂不直接拆除读写共用锁。若测量表明其为主要瓶颈，
   再进入第三轮；必须先解决同步失败时哪些版本可见、哪些提交可确认的问题。

**验收：** 同条件记录 P99、P99.9、最大停顿、吞吐、内存和维护频率。改善尾延迟时，
确认没有通过更弱同步、明显吞吐/内存退化或数据可见性变化换取成绩。若有取舍，单独
说明并重新评估，不概括为整体性能提升。

**第二轮实施结果（2026-11-17）：** 已完成可关闭阶段指标与 P99.9、硬链接封存 WAL
（不支持时复制回退）、按数据规模/修改量/维护成本调度快照、按队列负载调整合并等待。
捕获直接遍历共享节点；安装后的已覆盖 WAL 删除、目录同步与成功路径的快照副本释放
移到状态锁外，维护仍由独立快照锁串行化。未拆除读写共用锁，未改变提交可见性或格式版本。

同条件、关闭诊断的百万条三次中位数：更新 QPS 40,254 → 90,602（约 2.25 倍），
P99 0.290 → 0.175 ms，P99.9 1.108 → 0.934 ms，单轮最大延迟中位数
149.808 → 52.264 ms。后台 checkpoint 10 → 2 次；峰值 RSS 754.8 → 755.8 MiB，
profile 引擎稳态持有分配仍约 377.1 MiB。

取舍：最近快照加剩余 WAL 的重开 0.670 → 1.092 秒；第二轮三次中仍出现一次
162.20 ms 的最大更新延迟，热缓存读取 QPS 中位数下降 4.1%。不宣称所有指标均提升，
也不把最大停顿当作已彻底解决。1 万、10 万、100 万及 1/8/32 客户端结果、逐步阶段样本、
54 项单元与 22 个 SIGKILL 场景见
[第二轮优化报告](../pkg/metadata-engine/bench/ROUND2-OPTIMIZATION.md)。

### 14.4 第三轮：必要时再升级架构

进入条件：前两轮优化后，阶段指标仍证明全量快照捕获、锁竞争或全内存容量是主要限制。
这一轮是条件性架构评估，不要求同时实现所有候选。

| 候选 | 解决什么 | 新增成本与验证要求 |
| --- | --- | --- |
| 可冻结内存表与后台刷盘 | 切换写入表后后台处理旧表，减少全量持锁复制 | 跨表查询/有序扫描、多版本、合并、资源额度和安全回收 |
| 写时复制或固定读视图 | 降低读写互斥 | 旧版本生命周期、长读者导致的内存增长、提交可见性与回收边界 |
| 磁盘页索引 | 支持超过可接受内存容量的数据集 | 页缓存、页管理、随机 I/O、持久化与损坏恢复 |

借鉴来源：bbolt 的 Cursor 思路已用于现有有序扫描，读事务/写时复制可作为视图设计参考；
Pebble 的冻结表和刷盘可作为维护架构参考，但其 Snapshot 是逻辑读视图，不等同于当前
落盘 checkpoint。Badger 的事务版本和回收边界值得研究，Value Log 分离暂不优先：
当前值主要为小元数据，对象内容本就独立存储，额外 Value Log 会增加读取、恢复和 GC 成本。

**验收：** 先给出一个候选的设计、状态转换、所有权和故障矩阵，再单独实现验证。
以对应瓶颈确实改善为依据，同时核对新增读放大、写放大、内存和维护成本。没有明确
收益则保持现有结构；不因外部引擎采用某种结构就认定必须照搬。

**第三轮实施结果（2026-11-17）：** 已按上述进入条件选定并实现“仅供 checkpoint 的
固定读视图”，先形成[候选设计、所有权和故障矩阵](../pkg/metadata-engine/bench/ROUND3-DESIGN.md)。
捕获只保存元信息和节点指针、固定 payload；首次覆盖延迟释放旧值，由视图结束时回收。
单一视图由 checkpoint_mutex 管理完整生命周期，原子 pin 防止回收与覆盖竞争。
节点仍为 64 B，格式仍为 v2，未引入公开 MVCC、冻结表或磁盘页索引。

独立百万条阶段样本：最长捕获 92.7 → 8.7 ms；独立 profile 的捕获时引擎分配
696.6 → 438.1 MiB，未改变的键值不再全量复制。写入结束 RSS 701.3 → 429.7 MiB。
包含全量扫描的正式三次全流程峰值 RSS 中位数为 759.5 → 762.5 MiB，不能将阶段
内存节省等同于整个进程峰值下降。

百万条三次中位数：更新 QPS 91,442 → 88,473（下降 3.2%），P99 0.177 → 0.184 ms，
P99.9 1.155 → 1.094 ms，单轮最大延迟中位数 70.3 → 43.1 ms，但仍有一次 153.7 ms
长尾。10 万条 256 B 覆盖吞吐下降 9.1%，4 KiB 值补测则同时改善吞吐与尾延迟。
由于对应的捕获停顿和临时分配收益明确，保留此方案，同时记录全部退步；不宣称全面加速。
59 项 Debug/ReleaseSafe 测试、27 个 SIGKILL 场景及 60 秒混合模型通过，详见
[第三轮优化报告](../pkg/metadata-engine/bench/ROUND3-OPTIMIZATION.md)。

### 14.5 第四轮：长期行为、复杂事务与生产可靠性验证

这一轮主要补验证证据，不预设某个引擎更强。短时筛查可执行，超出当前时限的验证保留缺口。

| 维度 | 验证方案 | 判定边界 |
| --- | --- | --- |
| 冷缓存 | 热缓存重开与冷缓存读取分开；优先在可控制缓存的 Linux/NAS 环境运行，记录实际磁盘读取量 | 重开进程不等于冷缓存；不能把热读取结果当作冷盘能力 |
| 长期维护 | 同一进程固定键空间持续覆盖、删除和重新创建，观察内存、WAL、快照文件及停顿趋势 | 短测用于筛查；数小时/数日行为需真实持续运行，不能预测通过 |
| GC | 先验证 WAL 回收；tombstone 物理回收单独设计与测试 | 不能破坏 missing/exact 条件写及历史 generation 语义 |
| 复杂事务 | 多键原子修改、同键竞争、条件失败、批次冲突，以及事务期间重启和错误注入 | 已确认事务保留、失败事务无部分发布、恢复后的版本与顺序正确 |
| 生产可靠性 | ENOSPC、只读文件系统、同步失败、进程强杀、备份恢复和真实断电 | 注入不等于真实设备故障；未在目标平台实际验证的能力明确列为未验证 |

当前 Zig 不是 LSM，没有可直接与 Pebble 对齐的 compaction 操作。对照应比较持续写入后
维护所付出的时间、空间、前台停顿和数据正确性，不把不同类型的维护任务排成同一指标。

**验收：** 每项记录平台、工作负载、运行时长、故障方式、观察指标与结果。明确“实测通过”、
“失败”、“中止”、“预测”和“未验证”；生产成熟度不能由一次短压测或功能清单推断。

**第四轮实施结果（2026-11-17）：** 未发现需要改动生产引擎逻辑的问题，本轮新增独立
测试和可复现工具。Debug/ReleaseSafe 各 62 项测试、27 个 SIGKILL 场景通过；新增
96 条跨命名空间原子事务、八客户端 CAS 转账守恒，以及跨命名空间事务故障矩阵。

同一实例的 12,288 条记录 × 256 B 模型运行 300 秒，完成 7,881,020 次事务；
6,144 条 × 4 KiB 模型运行 120 秒，完成 1,867,644 次事务。两组重开校验一致，
引擎跟踪分配关闭后均归零；采样峰值 RSS 分别为 23.27 / 161.70 MiB。
大值组发生 181 次 WAL 额度重试并继续完成，但 RSS 仍呈上升趋势，不能宣称长期内存稳定。

真实 32 MiB HFS+ 临时卷上的 ENOSPC、释放空间后恢复、只读挂载检查与写模式拒绝通过；
停机全目录备份恢复、损坏快照和缺失 WAL 的拒绝检查通过。真实设备同步故障仍只有
注入证据，不能等同于实测断电保证。未新增 tombstone 物理 GC，也未重新排名外部数据库。
每项已运行用例均低于十分钟，长期正确性不以预测代替验证。详细指标、原始数据和复现命令见
[第四轮验证报告](../pkg/metadata-engine/bench/ROUND4-VALIDATION.md)。

### 14.6 执行顺序与外部对照依据

实际顺序：**分阶段指标 → 恢复顺序读缓冲 → 更新路径减少分配 → 索引内存优化 →
WAL 无复制轮转 → 快照调度 → 再评估冻结表/写时复制。** 第四轮的相关短时验证随改动
执行，长期与目标平台验证单独列出，不阻止先完成有证据支持的局部优化。

当前对照见 [数据量、耗时和内存总览](../pkg/metadata-engine/bench/EXTERNAL-COMPARISON.md)
及 [技术明细](../pkg/metadata-engine/bench/EXTERNAL-COMPARISON-DETAILS.md)。外部工具保持
独立 Go module，不向 ZigFS/Admin 添加依赖；保留源码、版本锁和原始结果。

对照必须统一 key、payload、批量、并发和结果复制规则，区分关闭工作与重开工作。
普通 KV 吞吐不能直接视为完整 MetadataRepository 接入后的吞吐；LSM flush/compaction、
bbolt 读快照与 Zig checkpoint 不能当成同一操作。不同缓存预算、同步等级和测试规模
不混排；预测耗时和未测内存不用于引擎选型结论。

现有补测中，10 万条完成四项配置、100 万条完成三项配置，四项长测仅给预测，一项
bbolt 测试中止。这些状态是后续计划的依据，不因本节列出优化方案而变成已完成验证。


## 15. 四轮之后补齐的维护功能（0.3.0）

按新增需求实现显式安全 tombstone 回收和在线备份，独立包仍未接入 ZigFS。
新库和文件统一采用 v3，不兼容旧格式。首次实际回收以后创建请求使用 missing_at，分页同时检查 generation/gc_epoch；旧 missing
失败关闭，不能静默将“历史删除”当成“从未存在”。回收世代持久化于 Snapshot v3，
回收不改变存活记录版本号，旧 exact 在键不存在或被新版本重建时均冲突。

在线备份使用固定视图而非复制正在变化的源目录；目标目录仅在完整同步后发布。
验证覆盖空库、全删除、重复回收、额度释放、旧条件拒绝、OOM、并发写入/回收/备份、
发布故障和新增 7 个 SIGKILL 边界。详细命令与结果见
[维护功能验证](../pkg/metadata-engine/bench/MAINTENANCE-VALIDATION.md)。
此前四轮报告是当时实现的历史记录；其中“无物理 GC”“仅停机备份”由本节更新。


## 16. ZigFS 接入（2026-11-18）

- 构建添加本地 metadata_engine 依赖，Docker 构建上下文改为仓库根以包含 pkg。
- Application 持有适配器和 Runtime，启动恢复引擎后重建业务索引；停机排空 Runtime 再关闭引擎。
- 唯一元数据目录为数据根下 `.zigfs.sys/`，没有额外 metadata 子目录。数据根格式主版本升为 3，
  引擎格式为 v3；不兼容旧库、不迁移、不自动删除损坏或未知格式。
- 删除旧 LocalMetadataRepository、LocalTransactionJournal、LocalRecoveryStore、record envelope、
  generation/检查点/扫描游标实现及仅用于这些实现的端口。保留业务 payload 和对象引用 GC。身份、角色/会话、策略、标签与系统配置按业务进入 13 个独立命名空间。
- 物理回收与业务 read/CAS 共用 state_mutex，适配器在此约束下把 missing 转为当前 missing_at。
  所有新增业务调用者必须遵守这一串行化规则；独立引擎的旧世代拒绝规则不变。
- 提供应用内 backupMetadata 导出在线元数据备份；引擎备份包含系统配置；完整 ZigFS 备份仍需对象、密钥、日志、事件队列和监控历史。
- 运行中不确定引擎写入使健康状态变成 Not Ready；恢复失败不静默重建空库。

运维与恢复步骤以 [备份与恢复](backup-and-recovery.md) 为准；前述四轮章节与报告保留当时历史状态。

本次接入的测试与实测记录见 [接入验证](metadata-engine-integration.md)。
