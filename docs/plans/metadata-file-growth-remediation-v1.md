# ZigFS 元数据小文件增长治理方案

- 日期：2026-11-11
- 状态：检查点、安全回收及运行期维护已实现；集中后端仍为后续选型
- 范围：ZigFS 元数据、事务日志、检查点、历史状态回收及后续集中存储
- 推荐路线：先完成检查点与安全回收，再基于规模测试决定集中元数据后端

当前实施约束：用户允许重建数据目录，不要求迁移或兼容此前的测试数据。
本轮不提供旧数据迁移工具；保留格式能力校验，防止不支持检查点的程序误用新数据目录。

## 1. 问题与目标

当前系统每次元数据变更都会生成独立事务日志文件；分片上传任务完成、取消或过期后，还会保留独立的删除标记文件。两者均缺少历史状态回收机制，导致文件数量持续增长。

这里的增长不是数学意义上的指数增长，而是**随累计元数据操作次数增长，并被分片数量、重试和事务阶段放大**。即使最终保留的业务文件很少，历史元数据文件仍可能很多。治理目标不是限制正常业务数据，而是消除历史操作造成的无界累积。

必须达到：

1. 已结束上传任务的历史标记可以安全回收。
2. 已稳定落盘的历史事务日志可以安全回收。
3. 持续运行时也能维护，不依赖服务重启。
4. 维护中断、进程崩溃或磁盘写入失败后，系统仍能确定正确状态。
5. 不删除正在上传的数据及任何已发布对象、历史版本仍引用的分片。
6. 在固定业务存量、持续重复上传和删除的负载下，历史文件数量经过维护后不再随累计操作数持续增加。

## 2. 当前实现与证据

### 2.1 本地数据快照

2026-11-11 对当前开发数据目录进行只读检查的结果如下。这是一次环境快照，不是性能基准。

| 目录 | 文件数 | 内容大小 | 文件系统分配空间 |
| --- | ---: | ---: | ---: |
| `zigfs/data/metadata/multipart` | 149 | 15,496 B | 610,304 B |
| `zigfs/data/.zigfs/journal` | 2,414 | 270,368 B | 9,887,744 B |

149 个 multipart record 均为 tombstone，每个 104 B，已检查记录类型、校验和及文件名与 key 哈希的一致性。文件系统分配空间来自 `st_blocks`，不同文件系统的结果可能不同。

这些记录只能证明任务已经结束，不能区分当时是成功完成、主动取消还是过期清理，也不能据此认定所有历史任务都来自用户手动上传。

### 2.3 写入与增长模型

现有成功提交路径：

```text
分配 generation
  → 持久化 intent 日志文件
  → 写入并同步临时 record
  → 持久化 commit 日志文件
  → rename 替换正式 record
  → 同步相关目录
```

同一 key 的正式 record 会被替换，不会为每次更新保留一个正式文件。但历史日志会持续增加，任务结束后的 tombstone 也不会消失。

在成功提交的简化场景下，若累计元数据提交次数为 M：

```text
历史 journal 文件数 ≈ 2 × M
multipart tombstone 文件数 ≈ 已结束且尚未回收的上传任务数
```

失败、回滚和其他业务操作还会改变实际数量。一个包含 P 个分片的成功上传，其任务创建、分片登记、对象发布、任务结束等操作都会贡献元数据提交；不能按最终业务文件数估计日志数量。

## 3. 一致性约束

### 3.1 不能直接删除 tombstone

当前恢复会检查历史已提交事务对应的正式 record。如果旧日志仍在，正式 record 和临时 record 却被删除，恢复可能报 `UnrecoverableTransaction`，使服务进入 `recovery_required`。

因此，“删除超过若干天的 record”不是安全方案。文件 mtime 也不是事务安全边界。

### 3.2 上传结束不代表分片实体可删

原实现完成上传后，正式对象的 multipart manifest 可能继续引用 `data/multipart/` 下的数据。任务元数据回收与数据实体回收必须分离；历史实体删除仍由引用关系和 GC 决定，覆盖当前对象及历史版本。本文末尾的补充实现将新上传改为先生成独立的完整逻辑对象，再持久化上传结束并清理临时分片。

### 3.3 检查点不是 generation 计数器的副本

generation 已分配不代表事务已经提交、发布或可靠落盘。检查点 C 必须表示：**所有 generation ≤ C 的事务均已解决，其最终正式状态已经持久化，恢复不再依赖这些事务的历史日志。**

不能简单读取最大 generation 后写入检查点。失败的提交、提交成功但发布失败的事务，以及仍在执行的写入，都必须纳入判断。

### 3.4 不掩盖真正的损坏

检查点只能排除已经证明可回收的历史事务。损坏或不受支持的检查点、检查点之后的损坏日志、缺失的有效元数据不能被当作“已清理”忽略。

## 4. 方案选择

| 方案 | 文件数量改善 | 复杂度与限制 | 决策 |
| --- | --- | --- | --- |
| 独立 record + 检查点 + 回收 | 消除历史日志和任务标记的无界累积 | 活跃元数据仍按条存文件 | 近期实施 |
| 定期全量重写单个 JSON/二进制 meta | 减少文件数 | 单条更新可能重写整个集合，并发与恢复成本高 | 不采用 |
| 自研快照 + 分段追加日志 + 压缩 | 文件数按段管理 | 需自行实现索引、恢复、半写处理、压缩和格式迁移 | 仅在明确要求原生自研时评估 |
| 嵌入式数据库，例如 SQLite | 集中存储元数据与事务状态 | 引入依赖，需迁移及性能验证 | 长期优先评估 |

单条逻辑 record 并不要求一个物理文件。当前布局利用文件系统原子替换降低实现复杂度，但不是协议要求。集中存储可以保留 record 的逻辑语义。

只追加一个 `deleted.meta` 仍会积累历史记录，并引入两套状态的一致性问题；不作为独立补丁采用。

## 5. 第一阶段：检查点与安全回收

### 5.1 格式和兼容性

引入带版本、校验和、存储实例标识、检查点 generation 的持久化检查点记录，使用临时写入、文件同步、原子替换、目录同步发布。

同时引入明确的存储格式版本或必需特性标记。旧版程序不理解检查点，不能继续读取已回收的旧布局。启用回收前必须确保版本拒绝机制有效；对不会识别该标记的历史二进制，需要通过发布与启动入口阻止降级，不能假设增加一个新文件就能让旧程序自动拒绝。

检查点覆盖的正式 record 继续作为当前状态来源；检查点本身不是备份或完整元数据快照。

### 5.2 维护协议

1. 获取全局元数据维护屏障，阻止新的元数据提交，等待已有提交退出。
2. 检查是否存在未解决事务。初版若发现此类状态，应停止本轮回收并进入明确的恢复流程；不得在在线业务请求中直接调用会修改磁盘状态但未同步内存索引的恢复过程。
3. 确认边界 C 之前的已提交记录及目录项已经持久化，回滚及临时文件处理完成。
4. 原子发布检查点 C，并同步其父目录。只有成功完成后才允许物理回收。
5. 释放维护屏障，允许新提交继续执行；新事务 generation 必须大于 C，分配器不得回退或重用旧值。
6. 后台分批删除 generation ≤ C 的旧 journal 文件，并同步受影响目录。
7. 分批检查 multipart tombstone，在仓库提交锁或等效保护下重新读取并确认其 generation ≤ C，且内容仍是待回收的同一版本，然后删除并同步目录。
8. 记录维护结果、未完成工作量与错误，失败后下一轮继续。

锁顺序必须结合现有 repository、journal、业务状态锁明确设计，不能在持有底层锁时反向获取业务锁。初版屏障期间若无法在预算内完成安全边界确认，应放弃本轮，不应无限阻塞请求。

同一 key 在清理期间可能产生新版本；后台任务不能仅凭第一次扫描得到的路径删除文件。首次仅回收 multipart tombstone，其他类型需单独审计其 generation、条件写入和业务语义。

### 5.3 恢复流程调整

```text
读取并验证存储格式与检查点 C
  → 筛选检查点之后的日志
  → 对 generation > C 的完整事务执行校验和恢复
  → 清理可确认的遗留临时文件
  → 重建元数据索引并验证对象引用
  → 服务就绪
  → 调度历史状态回收
```

需要在事务成组校验之前排除检查点覆盖的旧日志。否则清理中断后可能只剩下旧 commit、没有旧 intent，现有校验会误报日志不一致。

旧日志的识别必须有受约束、可验证的文件命名规则；不得把任意无法解析的文件静默归为已回收历史。文件名不可信或与内容不一致时应报告明确错误。对于检查点之外的日志，继续执行完整校验。

检查点损坏时不能自动退回 C=0，因为旧日志和 tombstone 可能已被合法删除；应停止恢复并报告故障。备份恢复必须恢复同一一致性集合。

### 5.4 崩溃与失败行为

| 中断位置 | 重启后的行为 |
| --- | --- |
| 新检查点发布前 | 使用旧检查点，所需旧状态尚未删除 |
| 新检查点已持久化，尚未删除旧文件 | 忽略其覆盖的历史事务，后续补做清理 |
| 只删除部分旧 journal | 不要求检查点内旧事务仍成对存在，继续清理 |
| 只删除部分 tombstone | 剩余标记仍表示任务结束，继续清理 |
| 检查点写入或同步失败 | 不开始基于该边界的任何删除 |
| 清理失败或权限不足 | 保留未删文件，告警并重试，不推进未经证明的边界 |
| 检查点之后的提交损坏 | 保持现有严格恢复失败语义 |

### 5.5 调度与可观测性

先实现启动恢复后的检查点和回收，用于验证协议；交付完整功能时必须同时支持运行期维护。

建议的初始调优起点：每 5 分钟检查一次，或累计 10,000 条旧日志时触发；单轮物理删除最多 1,000 个文件或持续 100 ms，先达到者结束。数值是待基准测试调整的建议，不是现有配置，也不构成文件数硬上限。

持续写入速率高于维护吞吐时仍会积压。需监测积压增长、磁盘余量和维护延迟，支持手动触发，并在必要时明确限制写入速率；不能通过牺牲持久性追赶清理速度。

至少记录以下指标：检查点 generation、最新 generation、journal 文件数与字节数、multipart 活跃任务数和 tombstone 数、待回收数量、本轮回收数、屏障耗时、维护耗时、最后成功时间及失败原因。数值尽量通过增量计数维护，避免每次请求全目录扫描。

如提供管理入口，应走 ZigFS Management API → BFF → Admin；Admin 不得直接操作数据目录。新增配置、API 和告警须同步更新文档。

## 6. 第二阶段：集中元数据后端评估

### 6.1 推荐候选

优先评估 SQLite，沿用现有 MetadataRepository 的业务抽象，替换物理布局、事务日志和恢复实现。不是只把 `get/put` 改成 SQL 后继续保留原独立 journal。

概念结构：

```text
metadata.db
  records(type, key, generation, payload)
  generation_state
  必要的维护与恢复状态
```

数据库以 `(type, key)` 为主键；条件写入在同一事务内校验 generation。删除记录后是否仍需保留逻辑 tombstone，由现有条件写入契约决定，不能一律替换为 SQL DELETE。multipart 任务可在语义验证后采用物理行删除。

数据库可能产生 WAL、共享内存及临时辅助文件，“集中 meta”不等于运行时只能存在一个文件。WAL 仍需要检查点，长时间读事务可能阻止其收缩；数据库行删除释放的页面通常供后续复用，不一定立即缩小文件。

### 6.2 仍需 ZigFS 保证的边界

- 对象数据和分片数据继续在文件系统中保存，数据库事务不覆盖这些外部文件。
- 保持先持久化实体数据、后发布元数据引用的顺序。
- 发布失败留下的数据由引用检查及 GC 回收。
- 评估将对象元数据发布与上传任务结束放入同一数据库事务，消除中间状态；这需要扩展当前跨服务事务接口。
- 不自动删除已有的应用层内存索引，先验证启动重建及查询成本。
- 明确同步级别、写锁等待、连接模型、数据库完整性检查和备份方式；不通过降低持久性换取性能。

### 6.3 选型门槛

对比现有后端加回收后的结果，测量 10,000、100,000 次任务及代表性对象存量下的吞吐、写入 P95/P99、启动时间、内存、磁盘占用、维护停顿和恢复时间。再决定是否正式替换。

若依赖约束排除 SQLite，自研方案必须包含分段追加日志、逐条长度与校验、提交边界、索引、快照原子切换、日志尾部半写处理、旧段回收及格式版本。不能只实现追加写入而没有压缩回收。

## 7. 迁移、备份与回退

第一阶段启用检查点也属于恢复协议变化；第二阶段集中存储属于更大范围的格式迁移。两者都需要明确升级路径。

1. 停止写入并完成旧格式恢复，确认无未解决事务。
2. 创建一致性备份，覆盖元数据、日志、generation 状态及与对象数据匹配的恢复集合。
3. 对第一阶段，发布格式能力标记和初始检查点后再启用回收。
4. 对第二阶段，导入临时数据库，校验记录数量、类型、generation、有效载荷和对象/分片引用。
5. 同步新存储，并原子切换表示唯一权威后端的格式清单。
6. 重启验证读取、上传、删除、版本和 GC，再启用写入。
7. 旧格式只作为离线备份保留，不进行双写或双后端自动回退。

切换前失败可以继续使用旧后端；切换并接受新写入后，旧备份已落后，不能仅切换开关回退。需要停机反向迁移或恢复备份并明确处理其后的写入。已回收历史日志后也不能直接运行不支持检查点的旧程序。

备份文档必须说明格式版本以及检查点与日志的一致性要求。SQLite 后端应使用受支持的一致性备份方式，不能在运行时只复制主数据库文件而漏掉未检查点的 WAL。

## 8. 实施拆分

| 步骤 | 交付内容 | 涉及位置 |
| --- | --- | --- |
| P0 | 增长统计、可复现负载、当前恢复失败用例 | conformance、metadata 测试、基准记录 |
| P1 | 检查点格式、兼容性门禁、恢复过滤、启动安全回收 | metadata/recovery、local_journal、local_repository、application 初始化 |
| P2 | 在线屏障、后台批量维护、状态和故障报告 | application 调度、metadata、配置和运维文档 |
| P3 | SQLite 原型、契约测试和规模对比，形成选型结论 | 新 metadata 后端、ports 契约测试 |
| P4 | 按选型结果完成格式迁移、备份与回退工具 | migration、release、backup 文档及 conformance |

P1 不能作为仅启动清理的最终交付；P1、P2 共同构成当前问题的完整修复。P3、P4 是长期演进，不能阻塞近期回收机制落地。

## 9. 验证与验收

### 9.1 功能和并发

- 完成、取消、过期任务均可回收 tombstone，活跃上传保持不变。
- 上传同一分片、重复结束请求、任务不存在等行为保持现有 API 语义。
- 已完成对象和历史版本的全部字节可读，校验和及 multipart ETag 不变。
- 同一 key 在后台扫描与删除之间被更新时，新 record 不会被误删。
- generation 单调增长，不因检查点、删除或重启重用。
- 当前未纳入回收范围的其他类型元数据不受影响。

### 9.2 故障注入

在检查点临时写入、文件同步、原子替换、目录同步、旧日志批量删除、tombstone 删除的前后分别中断进程。覆盖磁盘满、权限错误、I/O 失败、损坏检查点、部分旧事务日志残留、检查点之后的损坏日志，以及已提交但尚未发布的事务。

每个场景必须证明：可以正确恢复，或在确有无法恢复的损坏时明确拒绝启动；不能静默丢失已确认写入、恢复已结束任务或误删仍被引用的数据。维护重复运行应幂等。

### 9.3 规模与长期稳定性

使用隔离临时数据目录，分别运行 10,000 和 100,000 次任务，覆盖单分片、多分片、重试、取消和过期。固定有效对象/上传任务存量，持续重复操作并跨多轮维护和重启。

验收标准：

1. 写入停止且维护排空后，检查点覆盖的旧 journal 和符合条件的 multipart tombstone 不再残留；清理失败必须有可定位的错误。
2. 固定业务存量的持续负载中，历史文件数在维护周期内波动，不随累计任务数持续增长；维护吞吐足以覆盖声明支持的写入负载。
3. 同时报告文件数、逻辑字节、文件系统分配空间，不能只报告内容大小。
4. 记录并比较启动耗时、请求 P95/P99 和屏障耗时；性能门槛依据基线和部署目标确定，实施前写入基准报告，不虚构绝对收益。
5. 所有场景校验对象数据、版本引用及上传状态，不能只检查目录变空。

Zig 实现修改后执行：

```sh
cd zigfs
zig fmt --check src
zig build test
zig build
```

如改动 BFF 或 Admin，按仓库规范补充 `go test ./...`、`pnpm run build` 及相关交互检查。更新 `docs/backup-and-recovery.md`、配置文档和发布升级/回退文档；涉及管理 API 时同步 OpenAPI。

## 10. 当前落地范围

当前代码实现了实例绑定和校验保护的检查点、格式 required-feature flag、恢复前过滤旧事务、
启动维护和独立运行期维护任务。通过仓库提交锁建立短暂检查点屏障。
输入验证与载荷分配前置；失败事务只有在 abort 持久化、临时 record 删除和目录同步都成功后，
才视为安全回滚。提交不确定或回滚失败仍阻止本进程推进检查点，等待重启恢复。

回收范围已扩展到所有六类仓库 tombstone。业务状态锁保护读取 tombstone 后按版本重建的流程；
回收采用业务状态锁 → 仓库提交锁的顺序，重新校验候选。检查点之后发生的未解决重建事务可能
依赖旧 tombstone，因此回收每条候选时再次检查未解决状态，不能只在创建检查点时检查一次。
对象版本历史中的 S3 delete marker 不属于此处的仓库 tombstone。

实际默认周期为 60 秒，每轮分别最多访问 1000 个 journal 条目和 1000 个元数据条目；
活跃记录、无关文件也占用扫描预算。保留目录迭代游标，在各类元数据间轮流扫描，未完成时
下一轮等待 1 秒。活跃记录仅在锁外读取固定长度头部，候选才在锁内完整解码校验。
这限制了扫描工作量，但不是 100 ms 硬截止；没有新增按日志数量即时触发的计数器。

启动取得独占锁后、写入器启动前，清理内部目录白名单中的标准库原子写入临时文件。
只识别保留的 16 位小写十六进制文件名；不递归对象数据，不在线清理正在进行的原子发布。
新增真实子进程 SIGKILL 验证，以覆盖不会执行 defer 的中断，补充已有错误返回注入测试。

可观测性目前通过维护结果日志提供 generation、回收数、扫描数和耗时，尚未新增管理 API、
Admin 页面或 Prometheus 积压指标。集中 meta/SQLite 迁移不在本次实现范围内。

测试覆盖部分旧事务残留、检查点各发布阶段中断、标记删除中断、失败提交阻止维护、
维护期间的新写入、检查点损坏/缺失/实例错配/generation 回退，以及分片引用跨维护与重启保留。
生产吞吐与 P95/P99 仍需结合实际部署负载测量，不能将功能测试结果视为生产性能承诺。

新增隔离规模验证脚本 `conformance/metadata_maintenance.py`：生成校验有效的已提交任务
删除标记及 intent/commit 日志，启动真实 ZigFS 进程，等待后台清理完成，再重启验证。
脚本始终使用临时数据根，不接受已有数据目录；用于验证历史文件回收，不用于衡量上传吞吐。

```sh
python3 conformance/metadata_maintenance.py --tasks 10000 100000 --output /tmp/zigfs-metadata-maintenance-results.json
```

该脚本使用 1 秒周期、每类 10,000 个文件的批次，以缩短积压排空验证时间；这与生产默认
60 秒、1000 个文件不同。生成的历史文件只包含 multipart 标记及对应日志，不代表全部业务场景。

## 12. 四项复查问题的修复与验证

1. 安全回滚与未解决提交分开处理：大小验证错误不启动事务，已完整落盘的 abort 加临时
   record 清理成功不会暂停维护；回滚失败及提交后的发布失败继续要求恢复。
2. 启动清理原子写入孤儿：限定内部目录和临时文件名，取得独占锁后、任何写入器启动前执行。
3. 扩展回收至六类元数据：保留严格 generation 条件检查，使用业务状态锁保护同名重建。
4. 扫描预算覆盖全部访问条目：目录游标跨批次续扫，各类元数据轮流推进，活跃文件不再导致
   每次维护都全量重新读取；候选被替换或出现未解决事务时不会误删。

验证结果：`zig build test --summary all` 292/292 通过，`zig build` 通过；修改文件格式与
diff 检查通过。新增回归覆盖已确认 abort、abort 失败、全部类型删除后重建、过期 generation
冲突、活跃前缀中的扫描推进、检查点之后失败重建的恢复，以及业务状态锁下的并发条件写入。

真实进程中断及六类混合规模验证：

```sh
zig build-exe conformance/metadata_atomic_crash.zig -femit-bin=/tmp/zigfs-metadata-atomic-crash
python3 conformance/metadata_maintenance.py --tasks 10000 --all-types --crash-probe /tmp/zigfs-metadata-atomic-crash --output /tmp/zigfs-metadata-maintenance-all-types.json
```

在格式、generation、checkpoint、journal、日志配置的原子写入位置分别 SIGKILL 一个真实
子进程，确认目标文件未被半写替换，遗留临时文件全部在启动时清理。
10,000 条六类混合 tombstone 及其日志共 30,000 个文件，回收后剩 1 个检查点；统计目录
分配空间从 122,880,000 B 降至 4096 B。首次 Ready 7.525 s，从启动至排空 10.458 s，
排空后重启 Ready 0.112 s。该轮使用 1 秒周期和 10,000 条扫描预算，不代表生产上传吞吐。

另外只读核对了当前开发数据根中的 multipart 实体：15 个 `data` 文件合计 21,178,161 B，
全部有对象版本引用，没有发现未引用分片或缺失分片。它们属于有效对象数据，不属于应回收的
元数据标记；此次实现及验证未删除现有业务数据。


## 补充：上传分片与最终对象分离

完成上传采用“完整逻辑对象落盘 → 发布对象引用 → 持久化上传结束 → 清理临时分片”。
最终对象通过 ObjectDataStore 的 stage/publish 接口生成，不绑定单个物理文件的假设；
当前 LocalObjectDataStore 使用单文件，未来块后端仍可使用多个持久化物理块。
活跃上传保持集中式分片清单以支持断点续传。完成时逐片校验 SHA-256，保留 multipart ETag，
在上传结束标记持久化后清理全部临时分片，失败由引用感知 GC 补偿。

故障回归覆盖明文/加密两条路径的数据写入、数据同步、数据发布、对象元数据提交、
上传结束提交和清理失败；并覆盖重启续传、空末片、未选用分片清理和等长数据损坏。
恢复语义和磁盘空间开销见 `docs/backup-and-recovery.md` 的 multipart 实体目录说明。
