# CLI 上传并发优化验证（2026-11-18）

本文保留当时性能对照。最新分片和并发默认值以[统一客户端上传规则](../../../docs/client-upload-policy.md)为准；原 128 MiB 调度预算已移除。

## 实现

- 普通文件自动分片默认最多 4 路并发；`--part-concurrency 1..4` 可调整。标准输入仍串行。
- 可用逻辑 CPU 数是并发上限；当前验证机器为 10。多文件 `--concurrency` 额外保留 32 路硬上限，显式超限直接拒绝。
- 多文件传输按文件并发数分配分片预算，避免两级并发相乘超出 CPU 上限；大分片另按 128 MiB 调度预算减少路数。
- 请求使用独占借出的连接池句柄，归还前重置请求选项，保留可复用连接。最多缓存 32 个连接句柄。
- 所有在途分片结束后才返回失败或进行合并。检查点按编号记录已确认的连续前缀；后续已到达服务端但未写入检查点的片可在恢复时重传。
- 保留全文件和分片完整性校验、防覆盖条件以及结果不确定时拒绝自动合并的规则。
- 上传期间只显示整个文件的进度条、已传/总大小、合计平均速度、耗时和 ETA，不显示分片编号。恢复字节计入进度，但不计入本次上传速度。

## 实测

使用一个隔离的本地 Debug 服务，CLI 为 ReleaseSafe；128 MiB 文件、16 MiB 分片，同一版本分别设置单路和默认并发，每组 3 次交替运行。计时包含源文件哈希、分片传输、检查点及完成请求；每次下载并验证 SHA256。不是与浏览器瞬时速度的直接对比。

| 模式 | 第一次耗时 | 第二次耗时 | 第三次耗时 | 中位吞吐 |
|---|---:|---:|---:|---:|
| 单路 `--part-concurrency 1` | 6.114 s | 6.112 s | 6.185 s | 20.9 MiB/s |
| 默认 4 路 | 1.728 s | 1.737 s | 1.734 s | 73.8 MiB/s |

同版本对照约提升 **3.5 倍**。额外关闭上传连接复用的对照为单路 21.3 MiB/s、四路 73.7 MiB/s，因此未发现连接复用引入吞吐回退。早期命名为 baseline 的备份已包含并发实现，不能作为优化前版本证据，未用于上述结论。

复现（仓库根目录）：

```sh
python3 zigfs-cli/tests/upload_benchmark.py zigfs-cli/zig-out/bin/zc zigfs/zig-out/bin/zigfs
```

结果受 CPU、磁盘、服务负载、缓存和文件大小影响，不承诺所有环境或用户的 1 GiB 视频都达到同一速率。

## 回归证据

真实服务测试验证多个分片同时在途、HTTP/1.1 连接复用、分片响应丢失后保留连续检查点、恢复时跳过已确认片、源文件改变时拒绝恢复及合并响应丢失时拒绝盲目重试。CPU 超限测试要求联网前返回参数错误。

伪终端测试验证整体上传百分比单调、不显示分片编号、颜色和关闭开关、JSON/原始下载流隔离。S3 HTTP/TLS 回归与 CLI 单元测试一起执行。
