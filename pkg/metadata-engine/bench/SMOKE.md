# 本地压测烟测记录

日期：2026-11-17。Zig 0.17.0，ReleaseFast，macOS 26.2（25C56），aarch64。
测试目录位于本机 `/tmp`，所在 Data 卷约 460 GiB，测试时可用约 90 GiB。
未采集磁盘型号、挂载参数和峰值 RSS；CPU/内存详情受当前沙箱限制未取得。

这些是单次开发机烟测，不是容量或生产性能承诺，也没有与原文件仓库或 SQLite 做对照。
所有提交均调用文件 sync，操作系统缓存未清除；未做断电试验。重开时间是热缓存恢复。

## 复现命令

在 `pkg/metadata-engine` 运行，重复时使用新目录：

```sh
zig build bench -Doptimize=ReleaseFast -- /tmp/zigfs-metadata-final-single-20261117 10000 256 1 1
zig build bench -Doptimize=ReleaseFast -- /tmp/zigfs-metadata-final-batch-20261117 10000 256 32 8
```

## 结果

payload 均为 256 B，插入 10,000 条后再覆盖全部 10,000 条。
插入批次为 32 时，最后一批为 16 条，共 313 个事务；覆盖始终为单记录事务。

| 场景 | 操作 QPS | 事务 TPS | P50（μs） | P95（μs） | P99（μs） | 最大延迟（μs） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 单条同步插入 | 35,443.88 | 35,443.88 | 24.00 | 45.04 | 64.96 | 215.50 |
| 32 条批量插入 | 566,631.12 | 17,735.55 | 51.88 | 75.58 | 115.46 | 216.29 |
| 1 worker 同步覆盖 | 39,666.35 | 39,666.35 | 23.50 | 38.00 | 41.79 | 61.17 |
| 8 worker 同步覆盖 | 39,648.21 | 39,648.21 | 23.88 | 37.88 | 40.75 | 221,552.17 |

批量插入延迟是每个事务的延迟，不是批次中单条记录的独立延迟。
8 worker 的最大延迟约 **222 ms**，而 P99 只有约 41 μs：存在少量严重排队，P99 掩盖了
这些样本。当前互斥锁方案没有公平队列，多 worker 没有提高此轮吞吐；生产接入前需要
更长时间的并发测试与提交调度评估，不能只看 QPS 或 P99。

| 场景 | 单条插入运行 | 批量插入运行 |
| --- | ---: | ---: |
| 热内存 get QPS | 11,901,800.62 | 11,490,396.33 |
| 全量扫描排序（ms） | 3.544 | 3.704 |
| WAL 重放恢复（ms） | 25.402 | 16.010 |
| checkpoint（ms） | 17.966 | 17.367 |
| Snapshot 重开恢复（ms） | 16.731 | 16.650 |

热 get 读取内存 HashMap 并复制小 payload，不包含磁盘取对象、HTTP 或 S3 处理。
两次 WAL 恢复的数据相同，但事务数量不同（20,000 与 10,313），不能据此认为并发直接
加速了恢复。压测程序完成恢复后的 key、数量和 payload 校验，退出状态均为 0。

同期 `zig build test --summary all` 和 `zig build test -Doptimize=ReleaseSafe --summary all`
均通过 17/17 项测试。运行测试的 MaxRSS 分别约 4 MiB、2 MiB；这不是万条压测的峰值内存。
