# 安全 tombstone 回收与在线备份

日期：2026-11-17。独立包版本 0.3.0，仍未接入 ZigFS。
本次补齐两项维护能力，不重新进行数据库性能排名。

## 接口和使用边界

| 能力 | 接口 | 行为 |
| --- | --- | --- |
| 物理回收 | `engine.collectTombstones()` | 回收当前全部 tombstone、释放键和节点、收缩 HashMap、释放记录额度；返回回收数量和世代 |
| 在线备份 | `engine.backup(parent, name)` | 导出捕获时的一致数据库目录；返回 generation、gc_epoch、records；拒绝覆盖已有目标 |
| 缺失条件写入 | `.{ .missing_at = epoch }` | 仅在键不存在且世代仍匹配时提交 |
| 分页一致性 | `expected_generation` + `expected_gc_epoch` | 同时拒绝跨事务更新和跨物理回收的分页 |
| 运维 | `metadata-tool gc DIRECTORY` | 离线打开并显式回收，输出 stats；在线服务使用 Engine API |

回收是显式、阻塞式维护，持状态锁完成快照和索引切换，不是增量后台 GC。
后台普通 checkpoint 继续保留 tombstone。回收完成后，记录额度可供新键使用；
allocator 归还内存不承诺操作系统 RSS 立即降低。临时仍需新 HashMap 和存活记录视图数组。

在线备份捕获视图需要 O(N) 持锁遍历，随后流式编码与文件同步在状态锁外进行，
写入可以继续。备份与检查点、回收串行；慢目标可能推迟 WAL 回收，引起 ResourceLimit
背压，覆盖已固定记录也可能增加临时内存。目标目录应由调用者控制。

## 为什么不会让旧请求复活已删除数据

仅删除 tombstone 后继续允许旧 `.missing` 会丢失历史：一个很早之前发出的创建请求，
可能在删除标记被回收后意外成功。因此每次实际回收都推进一个全局 u48 `gc_epoch`，
并将新世代与“不含已回收键”的记录集写入同一个校验快照。

- 世代为零时，原 `.missing` 仍可用；首次实际回收后它一律返回 Conflict。
- `.missing_at` 要求当前世代匹配且键不存在。跨回收的过期请求不能仅因键消失而成功。
- 当前仍有 tombstone 时，missing_at 也冲突；保留删除版本的恢复写入使用 exact。
- `.exact` 要求当前存在的记录版本精确匹配。回收后键不存在，条件失败；重新创建分配
  更高的事务 generation，旧 exact 仍失败。存活键的 exact 不因其他键被回收而失效。
- `.any` 明确是无条件写入，不提供过期请求保护。
- 无 tombstone 时回收是空操作，不推进世代；u48 世代溢出时拒绝回收，不能回绕。

调用者必须在“不存在”的业务判断之前取得世代；Conflict 后重新执行业务判断，不能只
换一个新世代重发旧决策。该规则也适用于 Runtime 队列中的延迟请求。
世代是整个数据库的屏障，会使其他不存在键的旧创建请求也冲突，这是安全性与接口复杂度
之间的明确取舍。所有创建调用者采用 missing_at 之后再启用回收。

回收不消耗事务 generation，分页因此同时携带 generation/gc_epoch；省略世代视为零。
get/scan/page 返回的副本仍由调用者拥有，不会因回收而失效。

## 持久化与失败处理

回收先取得快照锁，再取得状态锁。预分配存活记录的新映射，轮转 WAL，生成不含
删除标记的新快照。文件同步、原子替换和目录同步完成后，才切换内存世代、释放节点
并重建 AVL；快照锁保证没有仍借用这些键和节点的检查点或备份。

| 失败阶段 | 行为 |
| --- | --- |
| 回收快照发布前 | 旧内存状态和旧快照/WAL 仍可恢复；安全的准备失败不冻结实例 |
| 回收快照发布结果不确定 | 冻结实例，重新打开；恢复以完整校验快照决定记录集和世代 |
| 回收已安装、旧 WAL 清理失败 | 回收已经生效，cleanup_pending 保留；可 retryCleanup，不能把返回错误当成回滚 |
| 备份发布前 | 不出现正式目标目录；普通失败清理私有临时目录，源库继续可用 |
| 备份发布后父目录同步失败 | 可能已有完整目标；inspect 后再决定重试，不覆盖已有目录 |
| 进程强杀留下备份临时目录 | 不视为成功备份；确认没有任务使用后可清理 `.metadata-backup-*` |

在线备份不复制正在轮转的源 WAL。它固定一个已确认视图，将完整记录写入独立 snapshot，
生成同 generation 的空 WAL 和 LOCK。同步文件与临时目录后，以不覆盖的 rename 发布
目标目录，再同步父目录。结果无源文件硬链接，打开备份继续写入不会影响源库。

恢复可以直接打开备份目录，或停掉目标引擎后将完整备份复制到新的专用目录。
恢复意味着时间点回退，应用必须废弃旧实例条件令牌；不能跨恢复沿用 generation/epoch。
包内备份不含 ZigFS 对象文件、外部凭证密钥等，不代替完整业务备份。

## 开发阶段格式决策

按用户要求，**不保留旧文件兼容，不做迁移**。新 WAL 和 Snapshot 文件头统一 v3，
只接受 v3；v1/v2 或未来版本返回 UnsupportedFormat，不修改、不自动覆盖旧文件。
停止旧实例后可以删除旧开发数据目录，再初始化新库。本次实现没有删除用户数据目录。

文件头仍为 80 B：字节 10–15 在 Snapshot 中保存小端 u48 gc_epoch，在 WAL 中必须为零，
包含在原 SHA-256 校验范围内。事务帧编码仍为帧版本 1；文件头与事务帧是不同版本字段。
Snapshot 要求各命名空间内键严格递增，不再保留旧无序快照的排序兼容分支。

## 验证

环境：macOS ARM64，Zig 0.17.0。验证源码纳入版本管理，生成的 results 目录继续忽略。

新增维护测试覆盖：

- 首次、重复、无操作、全 tombstone 回收；记录额度释放和多命名空间索引重建。
- 旧 missing、旧世代、旧 exact 和含过期条件的原子批次拒绝；存活记录 exact 保持有效。
- 回收世代经 checkpoint、备份、关闭重开保留；世代溢出拒绝和校验和损坏拒绝。
- 备份期间覆盖、插入、删除并继续写入，备份仍保留捕获时的视图。
- 并发写入、回收、备份保持跨命名空间事务一致；空库备份可独立打开并写入。
- 已有目标拒绝、路径参数检查、发布前失败、读模式导出、全部分配失败点和 pin 释放。
- 回收发布失败冻结、WAL 清理失败可重试；旧格式文件拒绝且不修改。

新增 7 个 SIGKILL 边界：回收快照同步后、发布后、目录同步后、旧 WAL 清理开始；
备份视图捕获后、文件/目录同步后、正式目录发布后。每次重新打开源库验证数据与世代，
备份发布前检查正式目录不存在，发布后检查可独立恢复并继续写入。

复现（在 `pkg/metadata-engine` 下）：

```sh
zig build test test-crash test-mixed --summary all
zig build test -Doptimize=ReleaseSafe --summary all
zig build -Doptimize=ReleaseSafe
```

最终结果：Debug / ReleaseSafe 各 73 项测试通过，34 个 SIGKILL 场景通过，短时混合模型
重开验证通过。ReleaseSafe 工具构建通过；实际 CLI gc 将六命名空间的 18 条记录回收至
12 条，释放 6 个 tombstone，重开后世代为 1，事务 generation 保持不变。
单项测试均未超过十分钟。本轮没有新增百万条回收停顿或备份吞吐性能结论。
真实断电、Linux/NAS、数小时至数日运行仍需目标平台验证；进程强杀不等同于断电。
