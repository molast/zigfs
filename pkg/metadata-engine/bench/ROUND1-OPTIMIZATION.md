# 第一轮优化实测：重开速度与内存

测试日期：2026-11-17。仅修改独立 `pkg/metadata-engine`，尚未接入 ZigFS。
所有表格均为本机实测，没有预测值；本轮未运行预计超过十分钟的用例。

## 先看时间和内存

每条 payload 为 256 B，键为 23 B；插入每批 32 条并同步，更新为 8 个并发客户端经 Runtime
提交单条事务，Group Commit 和后台 checkpoint 开启。以下为优化前后各三次的中位数。
“全部流程”包含插入、读取、覆盖、分页、全量扫描、两次重开和手动 checkpoint，
不是单纯写入时间；“进程峰值”是整个流程的 RSS，包含测试程序和临时副本。

| 数据量 | 全部流程：之前 → 之后 | 快照重开：之前 → 之后 | 重开速度 | 进程峰值：之前 → 之后 |
| --- | --- | --- | --- | --- |
| 1 万条 | 0.33 s → 0.30 s | 0.022 s → 0.006 s | 3.65 倍 | 12.5 → 13.6 MiB |
| 10 万条 | 3.41 s → 2.91 s | 0.223 s → 0.062 s | 3.58 倍 | 84.0 → 76.9 MiB |
| 100 万条 | 36.55 s → 35.32 s | 2.758 s → 0.685 s | 4.02 倍 | 806.6 → 742.6 MiB |

单位：1 MiB = 1,048,576 B。操作系统缓存未清空，因此这是热缓存重开，不能外推到冷启动。
新快照按键有序写入；旧无序快照仍能读取，但需要排序，不能套用这里的新快照重开加速比。

## 百万条：逐项看，不把所有指标混成一个排名

以下仍为三次中位数。QPS 是每秒处理的记录/操作数；P99 表示 99% 的更新请求在该时间内完成。

| 指标 | 之前 | 之后 | 变化 |
| --- | --- | --- | --- |
| 插入 100 万条所需时间 | 3.43 s | 3.62 s | 增加 5.7% |
| 热缓存读取 QPS | 4,303,602 | 4,765,617 | 增加 10.7% |
| 并发更新 QPS | 38,695 | 36,221 | 减少 6.4% |
| 更新 P99 | 0.36 ms | 0.44 ms | 增加 23.4% |
| 单轮最大更新延迟的中位数 | 127.21 ms | 236.94 ms | 增加 86.3% |
| 后台快照 + 剩余 WAL 重开 | 2965.74 ms | 772.95 ms | 减少 73.9% |
| 手动 checkpoint | 514.92 ms | 634.20 ms | 增加 23.2% |
| 快照重开 | 2758.00 ms | 685.29 ms | 减少 75.2% |
| 遍历全部分页 | 165.07 ms | 176.33 ms | 增加 6.8% |
| 全量排序扫描 | 173.97 ms | 179.92 ms | 增加 3.4% |

“WAL 重开”是原 benchmark 的字段名，实际会同时加载最近的后台快照和剩余 WAL，不是纯 WAL 回放。
同步策略保持不变，使用默认文件 sync；没有关闭持久化，也不是 macOS F_FULLFSYNC 对照。
三次重复只能反映本机短测，不能视为生产尾延迟分布或数据库总排名。
当前输出未采集 P99.9，仍待补齐。上表比较第一轮组合改动，未逐项做消融测试，
不将总加速比归因于某一个改动。1 万条进程峰值略增，内存也并非所有规模都下降。

## 百万条内存拆解

独立的 `profile` 运行记录 Engine allocator 的请求字节数。它不含分配器尺寸取整、
调用者拥有的读/扫描结果和 benchmark 数组；RSS 则包含整个进程的驻留内存。
两者口径不同，也会受 macOS 页面驻留/压缩影响，不能简单相减推算缓存大小。
以下 profile 前后各一次，只用于解释内存，不用于上方时间排名。

| 阶段/指标 | 之前 | 之后 |
| --- | --- | --- |
| 记录键和值的逻辑大小 | 266.1 MiB | 266.1 MiB |
| 插入完成：引擎持有分配 | 434.2 MiB | 377.1 MiB |
| 更新完成：引擎持有分配 | 434.2 MiB | 377.1 MiB |
| 快照副本存在：引擎持有分配 | 753.7 MiB | 696.6 MiB |
| 快照重开后：引擎持有分配 | 434.2 MiB | 377.1 MiB |
| 更新完成：进程 RSS | 771.2 MiB | 691.4 MiB |
| 快照重开后：进程 RSS | 774.2 MiB | 686.4 MiB |
| 引擎关闭后：引擎持有分配 | 0.0 MiB | 0.0 MiB |
| 引擎关闭后：进程 RSS | 636.6 MiB | 628.8 MiB |

引擎稳态请求分配减少约 57.1 MiB（13.2%）。百万条快照仍复制约 319.5 MiB 的键、值和
条目数组；这部分本轮没有消除。引擎关闭后跟踪分配归零，而 RSS 仍较高，说明释放给
allocator 不等于立即返还操作系统；RSS 还包含运行库等进程内存，不能等同于引擎泄漏。
因此，之前“约 800 MiB”不能直接称为百万条记录的稳态内存。

## 做了什么，以及代价

1. 恢复使用 64 KiB 顺序读缓冲，大于缓冲区的帧使用可复用存储；短尾、checksum、generation 链、文件身份检查保留。
2. 快照预扫描验证并统计各命名空间容量，再预留 HashMap。借用帧解码器复用条目数组，避免每条记录的临时帧分配。
3. 新快照按命名空间和键排序；恢复实际检查顺序，再批量建 AVL。旧无序 v1/v2 快照回退排序，未新增磁盘格式。
4. HashMap 改为持有共享记录节点，AVL 借用同一节点。覆盖更新只替换 payload 和元信息，保留原键和节点，不删除重插索引。
5. 增加可关闭的分阶段分配/RSS 记录和可重复的对照脚本。

预扫描会多读、校验一遍快照；新快照的有序复制也增加遍历开销。仍在共享锁下复制整个
快照，因此本轮不宣称解决了更新尾延迟。第二轮应继续优化 checkpoint 临界区和写入调度，
并用这里的 P99、最大延迟与 checkpoint 时间作为基线；冷缓存和长期行为留到后续轮次验证。

## 正确性和复现

- Debug 和 ReleaseSafe 各 45 项单元测试覆盖 CAS、事务、所有命名空间、配额、损坏与 OOM 清理；新增键/节点复用、混合更新失败回滚、批量恢复失败释放、跨缓冲区/大帧 WAL，以及旧无序快照/重复键测试。
- 18 个实际 SIGKILL 持久化边界场景；只允许活跃 WAL 的不完整尾部修复。
- 2 秒及 60 秒单进程混合参考模型验证通过。60 秒完成 1,158,920 个事务、18,110 次模型校验、4,931 次 checkpoint，重开校验通过。
  该模型只有 6 × 64 个键；RSS 从第 1 秒约 2.56 MiB 增至约 3.06 MiB，不能据此声称长期内存稳定或无泄漏。
- 每个性能用例检查读取/恢复后的数据与 generation，单用例 600 秒上限。本轮没有跳过后用预测冒充通过的正确性测试。

```sh
cd pkg/metadata-engine
zig build test
zig build test -Doptimize=ReleaseSafe
zig build test-crash test-mixed
zig build -Doptimize=ReleaseFast --prefix /private/tmp/metadata-round1-after
python3 bench/round1.py /private/tmp/metadata-round1-before/bin/metadata-bench \
  /private/tmp/metadata-round1-after/bin/metadata-bench \
  --output bench/results/round1-comparison.json
```

`before` 是改动前保存的二进制，不能用当前源码重编译替代。测试环境为 Apple M2 Pro、
16 GiB、macOS ARM64、Zig 0.17.0 ReleaseFast；二进制 SHA-256 见环境记录。
正式耗时对照关闭 profile，按 before/after、after/before、before/after 的顺序串行运行。
RSS 来自 `/usr/bin/time -l`，每个子进程单独统计。单例 profile 可加 `--profile-only`。
